# PCD-9799 `pcd_host` data source + PCD-9803 `network_labels` forces replacement

**Date:** 2026-09-04 · **Branch:** rename `claude/pcd-9799-9803-plan-b47da5` → `pushkar/pcd-9799-9803` before any push · **One PR, one commit per Jira plus one for the CE example**

## Context

Two bugs filed by Esten Rye on 2026-09-04 against `pcd-terraform-provider`:

- **[PCD-9799](https://platform9.atlassian.net/browse/PCD-9799)** — `pcd_host_config_assignment` (and `pcd_host_cluster_role`, `pcd_host_role`) need the resmgr host UUID, and nothing in the provider resolves it from the hypervisor's name. Users read it off the UI or `/etc/pf9/host_id.conf`. Acceptance: every UUID the provider needs is retrievable through a data source.
- **[PCD-9803](https://platform9.atlassian.net/browse/PCD-9803)** — resmgr answers 400 to any change of `networkLabels` on an existing host configuration, but `pcd_host_config` plans it as an in-place update, so changing a bond name fails every apply. Workaround today: rename the Terraform resource to force delete + create. Acceptance: a `network_labels` change plans a replacement.

Decisions you made during planning: one PR for both; the CE lab probe is approved; the Community Edition example and guide move to `pcd_host` in this PR.

## Findings that shape the design

- `network_labels` is `Optional + Computed` with no plan modifiers ([host_config_resource.go:88](internal/services/resmgr/host_config_resource.go:88)). The framework's `mapplanmodifier.RequiresReplace()` compares the planned value with state and treats *unknown* as a change (`requires_replace_if.go:62-65`). An `Optional + Computed` attribute left out of the config is planned unknown whenever anything else on the resource changes, so `RequiresReplace()` alone would replace the host config on a plain `name` edit when labels are unconfigured. `UseStateForUnknown()` must run first; the framework feeds each modifier's `PlanValue` into the next in slice order (`fwserver/attribute_plan_modification.go:1776`).
- Replacement ordering already works with the assignment. `host_config_id` is ForceNew on `pcd_host_config_assignment`, the new config's id is unknown at plan time, so the assignment is replaced too. Terraform destroys dependents first: unassign → delete config (the delete guard in `Delete` sees no assignment) → create config → assign. That is exactly the reporter's rename workaround. An assignment made outside Terraform still trips the guard, which already explains what to do.
- resmgr v2 `GET /hosts` records carry `id`, `roles` (cluster roles), `hostconfig_id`, `info.hostname`, `info.responding` (Platform9 KB article on force-removing hosts; the testsuite's `lib/api.py`; the provider's existing `hostAPI`). A host that has not reported yet has no `info`. `hostAPI` ([host_role_resource.go:161](internal/services/resmgr/host_role_resource.go:161)) is decoded from both v1 and v2 records, so adding an optional `info` field is safe for every caller.
- The `pcd_host_config` schema description is garbled — a sentence about the delete guard was spliced into the middle of a parenthesis ([host_config_resource.go:77-78](internal/services/resmgr/host_config_resource.go:77), visible in `docs/resources/host_config.md:6`). Fixed while editing this schema, since the new `network_labels` text refers to that guard.
- The CE lab currently lists **zero hosts and zero hypervisors** (`run.py api hosts`, 2026-09-04). The host-config probe and the `pcd_host_config` acceptance test need no host; the `pcd_host` acceptance test and the CE example validation do. Rebuilding the lab (create-ce-lab skill) is a prerequisite for those two, to be confirmed with you when we get there.

## Task 3 — PCD-9799: `pcd_host` data source

**New file:** `internal/services/resmgr/host_data_source.go`, modeled on [blueprint_data_source.go](internal/services/resmgr/blueprint_data_source.go).

| Attribute | Kind | Source |
|---|---|---|
| `name` | Required string | exact match on `info.hostname` (hosts usually report their FQDN) |
| `id` | Computed string | `id` — the resmgr host UUID |
| `roles` | Computed list of string | `roles` — cluster roles (`hypervisor`, `image-library`, …) |
| `host_config_id` | Computed string | `hostconfig_id`, empty when unassigned |
| `responding` | Computed bool | `info.responding` |

- `Read`: `ResmgrV2Client()`, `getJSONList(ctx, client, client.ServiceURL("hosts"), &hosts)` (the list is the authority, same as `hostsAssignedTo`), then a pure helper `hostByName(hosts []hostAPI, name string) (hostAPI, error)`: skips records with nil `Info`; 0 matches → error naming the known hostnames and noting that a host which has not reported yet has none; >1 → error.
- [host_role_resource.go:161](internal/services/resmgr/host_role_resource.go:161): add `Info *hostInfoAPI \`json:"info"\`` to `hostAPI` with `hostInfoAPI{Hostname string; Responding bool}`. Nothing else in `hostAPI` changes.
- [provider.go:129](internal/provider/provider.go:129): register `resmgr.NewHostDataSource`. Update the package comment in [resmgr.go](internal/services/resmgr/resmgr.go) to list the hosts data source.

## Risks and open points

- Whether resmgr accepts a PUT that carries unchanged labels: Task 1 answers it; if it does not, `Update` must omit `networkLabels` when unchanged (small follow-on change to `toAPI`, only if needed).
- Unassigning a host config from a host with converged roles may hit resmgr's 409 while converging; the replacement then fails and reapplies. Not new behavior (the rename workaround has the same exposure), but the changelog should say a replacement briefly leaves the host without a host configuration.
- `roles` and `responding` on the v2 record are documented from the KB article and testsuite, not from a live sample; the acceptance test confirms them before the docs ship.
